# cards Specification

## Purpose

Хранит карточки «вопрос — ответ» и предоставляет HTTP API для их просмотра и создания, сохраняя данные между перезапусками приложения.

## Requirements

### Requirement: Структура карточки
Каждая карточка SHALL иметь уникальный идентификатор `id` (UUID в строковом виде), непустой текст вопроса `question`, непустой текст ответа `answer` и признак `review` — находится ли карточка на повторении. В JSON-представлении карточка MUST содержать ровно поля `id`, `question`, `answer` (строки) и `review` (логическое значение). Новая карточка создаётся с `review: false`.

#### Scenario: Представление карточки в API
- **WHEN** клиент получает карточку через API
- **THEN** ответ содержит JSON-объект с полями `id`, `question`, `answer` строкового типа и полем `review` логического типа

#### Scenario: Новая карточка не на повторении
- **WHEN** клиент создаёт карточку через `POST /api/cards`
- **THEN** созданная карточка содержит `review: false`

### Requirement: Просмотр списка карточек
Система SHALL возвращать все сохранённые карточки по запросу `GET /api/cards` со статусом 200 в виде JSON-массива, упорядоченного по времени добавления (сначала самые старые).

#### Scenario: Список содержит карточки
- **WHEN** сохранены карточки A, затем B, и клиент выполняет `GET /api/cards`
- **THEN** система отвечает 200 и массивом `[A, B]`

#### Scenario: Пустой список
- **WHEN** карточек нет и клиент выполняет `GET /api/cards`
- **THEN** система отвечает 200 и пустым массивом `[]`

### Requirement: Просмотр одной карточки
Система SHALL возвращать карточку по запросу `GET /api/cards/{id}` со статусом 200. Если карточки с таким `id` нет, система MUST ответить 404 с JSON-телом, содержащим поле `error`.

#### Scenario: Карточка найдена
- **WHEN** клиент выполняет `GET /api/cards/{id}` для существующей карточки
- **THEN** система отвечает 200 и этой карточкой

#### Scenario: Карточка не найдена
- **WHEN** клиент выполняет `GET /api/cards/{id}` для несуществующего `id`
- **THEN** система отвечает 404 и JSON-объектом с полем `error`

### Requirement: Создание карточки
Система SHALL создавать карточку по запросу `POST /api/cards` с JSON-телом `{"question": ..., "answer": ...}`. Система MUST сама присвоить новый `id`, обрезать пробелы по краям вопроса и ответа и вернуть созданную карточку со статусом 201.

#### Scenario: Успешное создание
- **WHEN** клиент отправляет `POST /api/cards` с `{"question": "  2+2?  ", "answer": "4"}`
- **THEN** система отвечает 201 и карточкой с новым `id`, `question` = `"2+2?"` и `answer` = `"4"`
- **AND** карточка появляется в ответе `GET /api/cards`

#### Scenario: Переданный клиентом id игнорируется
- **WHEN** тело запроса на создание содержит поле `id`
- **THEN** система игнорирует его и присваивает карточке собственный `id`

### Requirement: Проверка входных данных при создании
Система MUST отклонять запрос на создание со статусом 400 и JSON-телом с полем `error`, если тело запроса — некорректный JSON или если `question` либо `answer` отсутствует, пустой после обрезки пробелов или длиннее 2000 символов. Отклонённая карточка MUST NOT сохраняться.

#### Scenario: Пустой вопрос
- **WHEN** клиент отправляет `POST /api/cards` с `{"question": "   ", "answer": "4"}`
- **THEN** система отвечает 400 с полем `error`, и число карточек не меняется

#### Scenario: Отсутствует ответ
- **WHEN** клиент отправляет `POST /api/cards` с `{"question": "2+2?"}`
- **THEN** система отвечает 400 с полем `error`

#### Scenario: Слишком длинный текст
- **WHEN** длина `question` или `answer` после обрезки превышает 2000 символов
- **THEN** система отвечает 400 с полем `error`

#### Scenario: Некорректный JSON
- **WHEN** тело запроса `POST /api/cards` не является корректным JSON
- **THEN** система отвечает 400 с полем `error`

### Requirement: Сохранность данных
Созданные карточки SHALL сохраняться в CSV-файле и MUST быть доступны после перезапуска приложения. Текст с запятыми, кавычками, переводами строк и не-ASCII-символами MUST сохраняться и читаться без искажений.

#### Scenario: Карточки переживают перезапуск
- **WHEN** карточка создана, а приложение перезапущено с тем же файлом данных
- **THEN** `GET /api/cards` возвращает эту карточку с теми же `id`, `question` и `answer`

#### Scenario: Специальные символы
- **WHEN** создаётся карточка с вопросом `Что такое "CSV", кратко?` и ответом из двух строк на кириллице
- **THEN** после перезапуска карточка читается с точно таким же текстом

#### Scenario: Файл данных отсутствует
- **WHEN** приложение запускается, а файла данных по настроенному пути нет
- **THEN** приложение создаёт файл с одной строкой заголовка и стартует с пустым списком карточек

### Requirement: Некорректный файл данных
Если существующий файл данных невозможно прочитать (неверный заголовок или повреждённая структура), приложение MUST завершить запуск с понятным сообщением об ошибке и MUST NOT перезаписывать этот файл. Допустимые заголовки — `id,question,answer,review` и прежний `id,question,answer`.

#### Scenario: Повреждённый файл
- **WHEN** файл данных существует, но его заголовок не `id,question,answer,review` и не `id,question,answer`
- **THEN** приложение не стартует, выводит сообщение с путём к файлу, а файл остаётся без изменений

### Requirement: Файл данных прежнего формата
Приложение SHALL читать файл данных с прежним заголовком `id,question,answer`, считая все карточки не на повторении (`review: false`). При первой записи файл MUST сохраниться в новом формате с заголовком `id,question,answer,review` без потери карточек.

#### Scenario: Запуск со старым файлом
- **WHEN** приложение запускается с файлом, у которого заголовок `id,question,answer` и две карточки
- **THEN** `GET /api/cards` возвращает обе карточки с `review: false`, а файл до первой записи не меняется

#### Scenario: Первая запись переводит файл в новый формат
- **WHEN** после запуска со старым файлом создаётся карточка
- **THEN** файл содержит заголовок `id,question,answer,review` и все три карточки, и после перезапуска они читаются без изменений

### Requirement: Отметка повторения
Система SHALL устанавливать признак повторения карточки по запросу `PUT /api/cards/{id}/review` с JSON-телом `{"review": true}` или `{"review": false}` и возвращать обновлённую карточку со статусом 200. Признак MUST сохраняться в файле данных и переживать перезапуск. Для несуществующего `id` система MUST ответить 404, для тела без логического поля `review` — 400; в обоих случаях с JSON-полем `error`.

#### Scenario: Пометить на повторение
- **WHEN** клиент выполняет `PUT /api/cards/{id}/review` с телом `{"review": true}` для существующей карточки
- **THEN** система отвечает 200 и карточкой с `review: true`, и после перезапуска карточка остаётся с `review: true`

#### Scenario: Снять с повторения
- **WHEN** клиент выполняет `PUT /api/cards/{id}/review` с телом `{"review": false}` для карточки на повторении
- **THEN** система отвечает 200 и карточкой с `review: false`

#### Scenario: Карточка не найдена
- **WHEN** клиент выполняет `PUT /api/cards/{id}/review` для несуществующего `id`
- **THEN** система отвечает 404 и JSON-объектом с полем `error`

#### Scenario: Некорректное тело
- **WHEN** клиент выполняет `PUT /api/cards/{id}/review` с телом `{}`, `{"review": "да"}` или некорректным JSON
- **THEN** система отвечает 400 и JSON-объектом с полем `error`

### Requirement: Случайная выборка карточек
Система SHALL возвращать по запросу `GET /api/cards/random?count=N` со статусом 200 JSON-массив не более чем из N разных карточек в случайном порядке. В выборку MUST сначала входить карточки на повторении (`review: true`), а оставшиеся места заполняются случайными карточками не на повторении. Если карточек на повторении больше N, в выборку попадают N случайных из них. Параметр `count` MUST быть целым числом от 1 до 100; иначе — 400 с JSON-полем `error`.

#### Scenario: Заданное количество
- **WHEN** сохранено 30 карточек, ни одна не на повторении, и клиент выполняет `GET /api/cards/random?count=10`
- **THEN** система отвечает 200 и массивом из 10 разных карточек из хранилища

#### Scenario: Карточки на повторении входят первыми
- **WHEN** сохранено 30 карточек, 3 из них на повторении, и клиент выполняет `GET /api/cards/random?count=10`
- **THEN** массив содержит 10 разных карточек, среди них все 3 карточки на повторении

#### Scenario: Карточек на повторении больше, чем запрошено
- **WHEN** на повторении 15 карточек, и клиент выполняет `GET /api/cards/random?count=10`
- **THEN** массив содержит 10 разных карточек, и все они на повторении

#### Scenario: Карточек меньше, чем запрошено
- **WHEN** сохранено 4 карточки, и клиент выполняет `GET /api/cards/random?count=10`
- **THEN** система отвечает 200 и массивом из всех 4 карточек

#### Scenario: Нет карточек
- **WHEN** карточек нет, и клиент выполняет `GET /api/cards/random?count=10`
- **THEN** система отвечает 200 и пустым массивом `[]`

#### Scenario: Случайный порядок
- **WHEN** сохранено 30 карточек, и клиент много раз выполняет `GET /api/cards/random?count=10`
- **THEN** наборы и порядок карточек в ответах различаются

#### Scenario: Неверное количество
- **WHEN** клиент выполняет `GET /api/cards/random?count=0`, `?count=101`, `?count=abc` или запрос без `count`
- **THEN** система отвечает 400 и JSON-объектом с полем `error`
