# Design

## Context

После `add-ui-screenshot-tests` в проекте есть npm-проект `ui-tests/` с Playwright Test, Node, который скачивает Gradle-плагин, задача `playwrightInstall` и хук Claude Code. Скриншотные тесты подменяют API и поэтому не проверяют связку «страница + сервер». Требования, которые нужно проверить, — шесть сценариев в `openspec/specs/cards-web-ui/spec.md` и пункт про недоступный сервер из требования «Ошибки при добавлении».

## Goals / Non-Goals

**Goals:**
- Каждый сценарий `cards-web-ui` проверяется автотестом на настоящем приложении и настоящем API.
- Тесты изолированы: каждый стартует с известного состояния данных и не зависит от порядка выполнения.
- Тесты запускаются в `./gradlew build` и через хук Claude Code.

**Non-Goals:**
- Подмена API: она остаётся только в скриншотных тестах.
- Тестовые эндпоинты вроде сброса данных: API приложения не меняется.

## Decisions

### 1. Отдельный конфиг `playwright.e2e.config.ts` и папка `ui-tests/e2e/`
Скриншотному конфигу нужен общий `webServer` и проекты с разными вьюпортами и темами, e2e — свой экземпляр приложения на каждый тест и один проект (Chromium, 1280×800). Раздельные конфиги не позволяют им мешать друг другу: e2e не запускает лишний `webServer`, а скриншотные тесты не подхватывают e2e-файлы.
- *Альтернатива — один конфиг с `testDir` по проектам.* `webServer` в Playwright глобальный и стартовал бы и для e2e.

### 2. Экземпляр приложения на каждый тест — фикстура `app`
Тестовая фикстура `app` (`ui-tests/e2e/app-fixture.ts`) делает следующее:
1. находит свободный порт (`net.createServer().listen(0)`);
2. создаёт пустой временный файл данных с уникальным именем;
3. запускает `java -jar $QUIZ_JAR --server.port=<порт> --quiz.data-file=<файл>`;
4. ждёт, пока `GET /api/cards` ответит 200 (таймаут 30 с);
5. отдаёт тесту `baseURL`, хелпер `createCard(question, answer)` для подготовки данных через `POST /api/cards` и метод `stop()`.

После теста фикстура завершает процесс и удаляет файл, в том числе при падении теста.
- Так сценарий «Нет карточек» проверяется на действительно пустом хранилище, а «сервер недоступен» — настоящей остановкой процесса через `app.stop()`, без подмены сети.
- *Альтернатива — один экземпляр на воркер и уникальные тексты карточек.* Быстрее, но «Нет карточек» без сброса данных не воспроизвести, а тесты начинают зависеть от порядка.
- Цена — около 2–3 с на старт приложения в каждом тесте. При 7 тестах и параллельных воркерах это примерно 20–40 с.

### 3. Соответствие сценариев и тестов
| Сценарий / требование | Тест (`ui-tests/e2e/cards-page.spec.ts`) |
|---|---|
| Открытие страницы | подготовить 3 карточки через API, открыть `/`, вопросы видны в порядке добавления, ответы скрыты |
| Нет карточек | пустое хранилище, видно сообщение «Карточек пока нет», список пуст |
| Показ и скрытие ответа | клик по второй карточке показывает её ответ, ответы остальных скрыты; повторный клик скрывает |
| Успешное добавление | заполнить форму и нажать «Добавить»: карточка последняя в списке, поля пусты, `GET /api/cards` содержит её, после перезагрузки страницы она на месте |
| Пустое поле | вопрос из пробелов и ответ «4»: видна ошибка с текстом «Вопрос», в поле ответа осталось «4», `GET /api/cards` пуст |
| Ошибки при добавлении: сервер недоступен | открыть страницу, `app.stop()`, отправить форму: видно сообщение о недоступности сервера, введённый текст сохранён |
| HTML в тексте карточки | карточка `<b>жирный</b><script>alert(1)</script>` через API: текст вопроса совпадает буквально, внутри вопроса нет элемента `b`, событие `dialog` не возникает |

Элементы находятся через доступные роли и тексты (`getByRole`, `getByLabel`, `getByText`), а не через CSS-классы. Тесты не ломаются от правок вёрстки, которые не меняют поведение. Исключение — проверка видимости ответа: она опирается на `toBeVisible()` и `toBeHidden()`, а не на класс `revealed`.

### 4. Задача Gradle `e2eTest`
`NpxTask` с `playwright test --config playwright.e2e.config.ts`, зависит от `bootJar` и `playwrightInstall`, передаёт `QUIZ_JAR`. Входы: jar (меняется при любом изменении бэкенда или статики), `ui-tests/e2e/**`, конфиг, lock-файл. Выход — маркер в `build/`. `check.dependsOn(e2eTest)`.

### 5. Хук
`.claude/hooks/screenshot-check.sh` переименовывается в `ui-check.sh`. Он запускает `./gradlew screenshotTest e2eTest -q` при правках в `src/main/resources/static/`. Правки Java-кода хук не трогает: их ловит `./gradlew build`, а гонять e2e на каждую правку бэкенда слишком дорого.

### 6. Ручная проверка больше не требуется
В `CLAUDE.md` раздел «Тестирование» дополняется так:
- сценарии `cards-web-ui` покрыты e2e-тестами;
- каждый новый сценарий UI в спецификации требует e2e-теста в том же изменении;
- в `tasks.md` новых изменений не должно быть шагов «проверить вручную в браузере», если сценарий можно автоматизировать.

## Risks / Trade-offs

- [Медленнее, чем подмена API] → параллельные воркеры и UP-TO-DATE-проверка. Тестов немного: по одному на сценарий.
- [Повисший процесс Java при аварийном завершении Playwright] → фикстура запускает процесс с `detached: false` и убивает его в teardown и в обработчике `process.on('exit')`. Порты случайные, поэтому повисший процесс не мешает следующему прогону.
- [Нестабильность из-за таймингов] → только автоожидающие проверки Playwright (`expect(...).toBeVisible()`) без `waitForTimeout`. Каждый тест проверяется на стабильность прогоном `--repeat-each=5`.
- [Тест «сервер недоступен» зависит от того, что `fetch` падает с сетевой ошибкой] → это ровно то поведение, которое описывает `app.js`, а настоящая остановка процесса воспроизводит его без подмен.
