# Design

## Context

Проект пустой: Gradle (Kotlin DSL), JDK 27, в `build.gradle.kts` есть только JUnit 5, в коде — демонстрационный `Main.java`. Это первое изменение, поэтому оно выбирает веб-стек, формат хранения и структуру пакетов для всего приложения. Требования — в `specs/cards/spec.md` и `specs/cards-web-ui/spec.md`.

## Goals / Non-Goals

**Goals:**
- Приложение собирается и запускается одной командой `./gradlew bootRun`.
- Хранилище за интерфейсом репозитория, чтобы CSV можно было заменить, не трогая сервисы и HTTP-слой.
- Бэкенд полностью покрыт автоматическими тестами, включая HTTP-уровень.

**Non-Goals:**
- Сборка фронтенда (npm, бандлер, TypeScript).
- Работа нескольких экземпляров приложения с одним файлом и защита от внешнего редактирования файла во время работы.
- Пагинация и поиск.
- Spring Data, JPA и любые СУБД.

## Decisions

### 1. Веб-фреймворк — Spring Boot
Используется Spring Boot (последняя стабильная версия, совместимая с JDK 27) со стартером `spring-boot-starter-web`. Он даёт встроенный сервер, REST-контроллеры, сериализацию JSON через Jackson, раздачу статики из `classpath:/static`, внедрение зависимостей и тестовую инфраструктуру (`spring-boot-starter-test`).
- *Альтернатива — Javalin.* Он легче и быстрее стартует, но при росте приложения (конфигурация, валидация, тесты срезов) многое пришлось бы собирать вручную. Spring Boot — стандарт в Java-экосистеме, и разработчику проще поддерживать знакомый стек.
- *Альтернатива — `com.sun.net.httpserver` из JDK.* Обходится без зависимостей, но статику, JSON, коды ошибок и тестовый клиент пришлось бы писать вручную.

Gradle-плагины: `org.springframework.boot` и `io.spring.dependency-management`. Версии зависимостей Spring берутся из BOM Boot.

### 2. Валидация — в сервисном слое, без Bean Validation
Правила (непустые значения после обрезки пробелов, не больше 2000 символов) проверяются в `CardService` и при нарушении выбрасывают `ValidationException`. Так правила тестируются без Spring-контекста и не дублируются между аннотациями DTO и сервисом.
- *Альтернатива — `spring-boot-starter-validation` с `@NotBlank` и `@Size` на DTO.* Аннотации проверяют значения до обрезки пробелов, поэтому сервису всё равно понадобилась бы своя проверка.

### 3. CSV — Apache Commons CSV
Библиотека корректно поддерживает RFC 4180: кавычки, запятые и переводы строк внутри значений. Писать собственный парсер рискованно, а `split(",")` не подходит.
- *Альтернатива — OpenCSV.* Возможности примерно те же, но у Commons CSV меньше транзитивных зависимостей и проще API для строгого заголовка.

Версия Commons CSV — последняя стабильная на момент реализации.

### 4. Модель хранения: весь набор в памяти, файл перезаписывается целиком
`CsvCardRepository` — Spring-бин. При создании он читает файл целиком в `List<Card>`, порядок строк равен порядку добавления. Чтение данных идёт из памяти. При создании карточки новый список записывается во временный файл в той же директории, после чего тот атомарно заменяет основной (`Files.move` с `ATOMIC_MOVE` и `REPLACE_EXISTING`). Только после успешной записи изменение попадает в память.
- Доступ синхронизирован через `ReentrantReadWriteLock`: контроллеры Spring обслуживают запросы параллельно.
- *Альтернатива — дописывать строку в конец файла (append).* Так быстрее, но частичная запись может повредить файл. При ожидаемом объёме (сотни или тысячи карточек) полная перезапись дешёвая.

Формат файла: UTF-8 без BOM, заголовок `id,question,answer`, обрамление значений кавычками там, где это нужно по RFC 4180. Если заголовок не совпадает, конструктор бина выбрасывает исключение с путём к файлу. Контекст Spring не поднимается, приложение завершается с этим сообщением, а файл не трогается.

### 5. Слои и пакеты
```
org.valgor.quiz
├── QuizApplication          — @SpringBootApplication, точка входа
├── config/QuizProperties    — @ConfigurationProperties("quiz"): путь к файлу данных
├── model/Card               — record (id, question, answer)
├── repository/CardRepository, CsvCardRepository (@Repository)
├── service/CardService (@Service) — валидация, обрезка пробелов, генерация UUID
│   └── ValidationException, CardNotFoundException
└── web/
    ├── CardController (@RestController, /api/cards)
    ├── CreateCardRequest    — record (question, answer); поле id в нём отсутствует, поэтому игнорируется
    └── ApiExceptionHandler (@RestControllerAdvice) — 400/404 + {"error": "..."}
```
`ApiExceptionHandler` обрабатывает `ValidationException` (400), `HttpMessageNotReadableException` — некорректный JSON (400) — и `CardNotFoundException` (404). Тело ответа — `record ErrorResponse(String error)`. `Main.java` удаляется.

### 6. Конфигурация
В `src/main/resources/application.properties`:
- `quiz.data-file=data/cards.csv` — недостающие директории создаются при старте;
- `server.port=8080`.

Оба значения переопределяются стандартными механизмами Spring, в том числе переменными окружения `QUIZ_DATA_FILE` и `SERVER_PORT` (relaxed binding).

### 7. Фронтенд — статичные HTML + vanilla JS
Файлы `src/main/resources/static/index.html`, `app.js` и `styles.css` Spring Boot раздаёт автоматически, а `index.html` открывается по адресу `/`. Карточки выводятся только через `textContent`, без `innerHTML` с данными, — так выполняется требование о безопасном выводе текста. Раскрытие ответа переключает CSS-класс.
- *Альтернатива — Thymeleaf.* Серверный рендеринг не нужен: страница и так работает через API.
- *Альтернатива — React или Vue со сборкой.* Для одной страницы это избыточно, к тому же понадобился бы Node в процессе сборки.

### 8. Тестирование
- `CsvCardRepository`: обычные JUnit-тесты без Spring на реальных файлах в `@TempDir` (специальные символы, перезапуск, отсутствующий и повреждённый файл).
- `CardService`: юнит-тесты с репозиторием в памяти (тестовая реализация `CardRepository`), без Spring и файловой системы.
- HTTP API: `@SpringBootTest` с MockMvc. `quiz.data-file` указывает на временный файл через `@DynamicPropertySource`. Тесты проверяют все сценарии `cards`.
- Перезапуск: тест создаёт карточку, затем поднимает второй контекст через `SpringApplicationBuilder` на том же файле и проверяет, что карточка на месте.
- Веб-интерфейс: автоматически проверяется только то, что `/` отдаёт HTML. Поведение страницы (раскрытие ответа, форма, ошибки, экранирование) проверяется вручную в браузере по сценариям `cards-web-ui`; браузерные автотесты — кандидат на отдельное изменение.

## Risks / Trade-offs

- [Spring Boot тяжелее: дольше старт и больше зависимостей] → для одного локального приложения это приемлемо. Взамен — стандартный стек и готовая инфраструктура для следующих изменений.
- [Поддержка JDK 27 в текущей версии Spring Boot] → проверить в задаче 1.1. Если сборка или запуск не работает, понизить toolchain до последней LTS, которую Boot официально поддерживает, и отметить это в `CLAUDE.md`.
- [Полная перезапись файла медленнее при большом числе карточек] → для учебного объёма это несущественно. Если понадобится, можно перейти на другой репозиторий за тем же интерфейсом.
- [Ручное редактирование CSV во время работы приложения будет перезаписано] → описать в `CLAUDE.md`: редактировать файл только при остановленном приложении.
- [`ATOMIC_MOVE` не поддерживается на некоторых файловых системах] → временный файл создаётся в той же директории. При `AtomicMoveNotSupportedException` бросается понятная ошибка, без молчаливого перехода на неатомарную запись.
- [UI не покрыт автотестами] → чек-лист ручной проверки в задачах. Браузерные тесты отложены осознанно.

## Migration Plan

Миграция не нужна: данных ещё нет. Если файла нет, он создаётся при первом запуске. Откат — удалить `data/cards.csv` и вернуть предыдущую версию кода.
