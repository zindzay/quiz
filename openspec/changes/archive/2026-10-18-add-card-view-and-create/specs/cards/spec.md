# Spec Delta

## Purpose

Хранит карточки «вопрос — ответ» и предоставляет HTTP API для их просмотра и создания, сохраняя данные между перезапусками приложения.

## ADDED Requirements

### Requirement: Структура карточки
Каждая карточка SHALL иметь уникальный идентификатор `id` (UUID в строковом виде), непустой текст вопроса `question` и непустой текст ответа `answer`. В JSON-представлении карточка MUST содержать ровно поля `id`, `question`, `answer`.

#### Scenario: Представление карточки в API
- **WHEN** клиент получает карточку через API
- **THEN** ответ содержит JSON-объект с полями `id`, `question`, `answer` строкового типа

### Requirement: Просмотр списка карточек
Система SHALL возвращать все сохранённые карточки по запросу `GET /api/cards` со статусом 200 в виде JSON-массива, упорядоченного по времени добавления (сначала самые старые).

#### Scenario: Список содержит карточки
- **WHEN** сохранены карточки A, затем B, и клиент выполняет `GET /api/cards`
- **THEN** система отвечает 200 и массивом `[A, B]`

#### Scenario: Пустой список
- **WHEN** карточек нет и клиент выполняет `GET /api/cards`
- **THEN** система отвечает 200 и пустым массивом `[]`

### Requirement: Просмотр одной карточки
Система SHALL возвращать карточку по запросу `GET /api/cards/{id}` со статусом 200. Если карточки с таким `id` нет, система MUST ответить 404 с JSON-телом, содержащим поле `error`.

#### Scenario: Карточка найдена
- **WHEN** клиент выполняет `GET /api/cards/{id}` для существующей карточки
- **THEN** система отвечает 200 и этой карточкой

#### Scenario: Карточка не найдена
- **WHEN** клиент выполняет `GET /api/cards/{id}` для несуществующего `id`
- **THEN** система отвечает 404 и JSON-объектом с полем `error`

### Requirement: Создание карточки
Система SHALL создавать карточку по запросу `POST /api/cards` с JSON-телом `{"question": ..., "answer": ...}`. Система MUST сама присвоить новый `id`, обрезать пробелы по краям вопроса и ответа и вернуть созданную карточку со статусом 201.

#### Scenario: Успешное создание
- **WHEN** клиент отправляет `POST /api/cards` с `{"question": "  2+2?  ", "answer": "4"}`
- **THEN** система отвечает 201 и карточкой с новым `id`, `question` = `"2+2?"` и `answer` = `"4"`
- **AND** карточка появляется в ответе `GET /api/cards`

#### Scenario: Переданный клиентом id игнорируется
- **WHEN** тело запроса на создание содержит поле `id`
- **THEN** система игнорирует его и присваивает карточке собственный `id`

### Requirement: Проверка входных данных при создании
Система MUST отклонять запрос на создание со статусом 400 и JSON-телом с полем `error`, если тело запроса — некорректный JSON или если `question` либо `answer` отсутствует, пустой после обрезки пробелов или длиннее 2000 символов. Отклонённая карточка MUST NOT сохраняться.

#### Scenario: Пустой вопрос
- **WHEN** клиент отправляет `POST /api/cards` с `{"question": "   ", "answer": "4"}`
- **THEN** система отвечает 400 с полем `error`, и число карточек не меняется

#### Scenario: Отсутствует ответ
- **WHEN** клиент отправляет `POST /api/cards` с `{"question": "2+2?"}`
- **THEN** система отвечает 400 с полем `error`

#### Scenario: Слишком длинный текст
- **WHEN** длина `question` или `answer` после обрезки превышает 2000 символов
- **THEN** система отвечает 400 с полем `error`

#### Scenario: Некорректный JSON
- **WHEN** тело запроса `POST /api/cards` не является корректным JSON
- **THEN** система отвечает 400 с полем `error`

### Requirement: Сохранность данных
Созданные карточки SHALL сохраняться в CSV-файле и MUST быть доступны после перезапуска приложения. Текст с запятыми, кавычками, переводами строк и не-ASCII-символами MUST сохраняться и читаться без искажений.

#### Scenario: Карточки переживают перезапуск
- **WHEN** карточка создана, а приложение перезапущено с тем же файлом данных
- **THEN** `GET /api/cards` возвращает эту карточку с теми же `id`, `question` и `answer`

#### Scenario: Специальные символы
- **WHEN** создаётся карточка с вопросом `Что такое "CSV", кратко?` и ответом из двух строк на кириллице
- **THEN** после перезапуска карточка читается с точно таким же текстом

#### Scenario: Файл данных отсутствует
- **WHEN** приложение запускается, а файла данных по настроенному пути нет
- **THEN** приложение создаёт файл с одной строкой заголовка и стартует с пустым списком карточек

### Requirement: Некорректный файл данных
Если существующий файл данных невозможно прочитать (неверный заголовок или повреждённая структура), приложение MUST завершить запуск с понятным сообщением об ошибке и MUST NOT перезаписывать этот файл.

#### Scenario: Повреждённый файл
- **WHEN** файл данных существует, но его заголовок не `id,question,answer`
- **THEN** приложение не стартует, выводит сообщение с путём к файлу, а файл остаётся без изменений
