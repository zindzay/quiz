# Design

## Context

Интерфейс — одна статическая страница `src/main/resources/static/index.html` + `app.js`: форма добавления и список карточек с раскрытием ответа. Страницы отдаёт Spring Boot как статику, вёрстка — Bootstrap 5 (WebJar), тема — `theme.js`, свои классы — с префиксом `quiz-`. API: `GET /api/cards`, `GET /api/cards/{id}`, `POST /api/cards`. Поведение интерфейса покрыто e2e-тестами (`ui-tests/e2e/`), внешний вид — скриншотами (`ui-tests/tests/`, эталоны `-darwin`). Требования — delta-спецификации этого изменения: `quiz-session` (новая), `cards`, `cards-web-ui`.

## Goals / Non-Goals

**Goals:**
- Три самостоятельные страницы: тест (`/`), добавление (`/add.html`), все карточки (`/cards.html`).
- Случайная выборка на сервере — воспроизводимо тестируемая JUnit.
- Ход теста — на клиенте; на сервере сохраняется только отметка повторения карточки.
- Существующие файлы данных продолжают работать без ручной миграции.

**Non-Goals:**
- Фреймворки фронтенда, сборка JS, клиентский роутинг.
- Сохранение итогов тестов, статистика, интервальное повторение с расписанием.

## Decisions

### 1. Признак повторения и формат CSV (миграция)
- `Card` — `record(id, question, answer, boolean review)`; `POST /api/cards` создаёт карточку с `review = false`, тело запроса по-прежнему `{question, answer}`.
- CSV: заголовок `id,question,answer,review`, значение `review` — `true` или `false`.
- **Миграция без отдельного шага.** `CsvCardRepository` при чтении принимает два заголовка: новый и прежний `id,question,answer` (тогда `review = false` у всех карточек). Файл при чтении не меняется; первая запись (`save` или обновление) переписывает его целиком атомарно в новом формате. Другой заголовок или неверное число полей — по-прежнему `DataFileException` без перезаписи файла. Значение `review`, отличное от `true` и `false`, — тоже ошибка формата.
- `CardRepository` получает метод `update(Card)` — замена карточки с тем же `id` с атомарной перезаписью файла под той же блокировкой записи.
- Откат: прежняя версия приложения не прочтёт файл с колонкой `review`. Для отката достаточно удалить колонку — например, открыть файл в табличном редакторе при остановленном приложении. Это отмечено в README.
- *Альтернатива — отдельный файл `review.csv` со списком `id`.* Формат основного файла не меняется, но появляется второй источник данных, который нужно держать согласованным при создании карточек и сбоях записи.
- *Альтернатива — хранить отметку в браузере (localStorage).* Не требует изменений сервера, но отметки пропадают при очистке браузера и не видны с другого устройства. Пользователь выбрал хранение на сервере.

### 2. Отметка повторения — `PUT /api/cards/{id}/review`
Тело `{"review": true|false}`; ответ — обновлённая карточка. Тело без логического `review` — 400 «Поле review обязательно и должно быть true или false», неизвестный `id` — 404 (существующие `CardNotFoundException` и `ApiExceptionHandler`). Метод идемпотентен: повторный запрос с тем же значением ничего не меняет и возвращает 200.
- *Альтернатива — `POST /api/cards/{id}/answers {known}`.* Ближе к языку теста, но сервер всё равно хранит только признак; `PUT` состояния проще и идемпотентен.

### 3. Случайная выборка — на сервере, `GET /api/cards/random?count=N`
`CardService.random(int count)` проверяет диапазон 1–100 (иначе `ValidationException` → 400 «Количество должно быть целым числом от 1 до 100»). Затем делит карточки на «на повторении» и остальные, перемешивает обе группы `Collections.shuffle` с `Random`, переданным в конструктор (в тестах — с фиксированным зерном), берёт сначала из первой группы, потом из второй, всего `min(count, size)`, и перемешивает итоговый набор, чтобы вопросы на повторении не шли всегда первыми. Контроллер принимает `count` строкой и разбирает сам, чтобы `abc` и отсутствие параметра давали тот же 400 с понятным `error`, а не стандартную ошибку Spring. Литеральный путь `/random` имеет приоритет над шаблоном `/{id}` — это проверяется тестом API.
- *Альтернатива — перемешивать на клиенте результат `GET /api/cards`.* Без нового API, но клиент получает всю базу ради 10 карточек, а случайность не покрыть JUnit.

### 4. Три статические HTML-страницы
- `index.html` + `quiz.js` — тест;
- `add.html` + `add.js` — форма (логика формы переезжает из `app.js`);
- `cards.html` + `cards.js` — список (логика списка из `app.js`); `app.js` удаляется.

Навигация — одинаковая разметка Bootstrap `nav nav-pills` в шапке каждой страницы; текущая ссылка — класс `active` и `aria-current="page"`. Разметка дублируется в трёх файлах: это проще и надёжнее, чем вставлять её скриптом, — страница оформлена до загрузки JS, а e2e находят ссылки по ролям. Общих JS-модулей нет: у страниц нет общей логики, кроме `fetch` с обработкой ошибок, а её проще повторить в трёх небольших файлах, чем вводить модули без сборки.

### 5. Тест — конечный автомат на одной странице
Ответ «Знал» / «Не знал» сначала отправляет `PUT /api/cards/{id}/review` (`false` / `true`) и только после успешного ответа засчитывается и показывает следующую карточку; на время запроса кнопки блокируются. При ошибке — сообщение, карточка и кнопки остаются (требование «Ошибка сохранения ответа»). Карточка с `review: true` получает бейдж Bootstrap «На повторении».

Экраны: **выбор** (поле «Количество вопросов», `input type=number min=1 max=100 value=10`, кнопка «Начать тест», место для ошибки) → **вопрос** (подпись «Вопрос N из M» в области `aria-live="polite"`, карточка, кнопки «Знал» / «Не знал») → **итог** («Знал K из M», кнопка «Новый тест»). Экраны — секции с атрибутом `hidden`, состояние — переменные `cards`, `index`, `known`. Кнопки «Знал» / «Не знал» скрыты, пока ответ не показан, — так вернуться назад или пропустить вопрос просто нечем. Количество проверяется на клиенте (сообщение без запроса к серверу) и повторно на сервере.

Если карточек меньше запрошенного, над карточкой показывается «В тесте M вопросов — карточек в базе меньше, чем запрошено». Если карточек нет — экран выбора с сообщением и ссылкой «Добавить карточки».

### 6. Квадратная карточка
`.quiz-test-card`: `aspect-ratio: 1 / 1`, ширина `min(100%, 26rem)`, по центру; содержимое — flex-колонка по центру с прокруткой при длинном тексте (до 2000 символов); вопрос крупнее обычного текста; ответ появляется под вопросом с разделителем, как в списке. Карточка — `role="button"`, `tabindex="0"`, `aria-expanded`; раскрытие по клику, Enter и Пробел, как у карточек списка. Цвета — только переменные Bootstrap.

### 7. Тестирование
- **JUnit:** `CsvCardRepositoryTest` — запись и чтение `review`, чтение файла прежнего формата без изменения файла, перевод в новый формат при первой записи, `update`, неверное значение `review`; `RestartPersistenceTest` — `review` переживает перезапуск; `CardServiceTest` — выборка заданного числа без повторов, карточки на повторении входят первыми, на повторении больше N, меньше карточек, пусто, неверное количество, различие порядка при разных зёрнах, отметка повторения; `CardApiTest` — `review` в JSON, `POST` создаёт `review: false`, `PUT .../review` (200, 404, 400 для `{}`, строки и некорректного JSON), выборка (200 и размер, приоритет повторения, 400 для `0`, `101`, `abc`, без параметра, `/random` не попадает в `/{id}`); `StaticPageTest` — отдача `/`, `/add.html`, `/cards.html`.
- **E2E (`ui-tests/e2e/`):**
  - `quiz-page.spec.ts` — все сценарии `quiz-session` на настоящем приложении (фикстура `app`): 10 из 30 разных, 4 из 10, нет карточек, неверное количество, показ ответа, последовательность, итог, новый тест, сервер недоступен, HTML в тексте; повторение — «Не знал» возвращает вопрос в следующий тест (проверка по хранилищу через `app.listCards()` и по составу нового теста), вопрос возвращается до ответа «Знал», «Знал» снимает с повторения, прерванный тест сохраняет отметку, пометка «На повторении», ошибка сохранения ответа (сервер остановлен перед ответом);
  - текущий `cards-page.spec.ts` делится на `add-page.spec.ts` и `cards-list.spec.ts` с новыми адресами;
  - `theme.spec.ts` и `external-resources.spec.ts` проходят по всем трём страницам; навигация — отдельный тест.
- **Скриншоты (`ui-tests/tests/`):** ответы API подменяются фикстурами, `GET /api/cards/random` — фиксированным набором. Состояния: тест — выбор, вопрос, ответ показан, итог, нет карточек, ошибка, тёмная тема, мобильный вид; добавление — форма, ошибка, успех; список — карточки, пусто, раскрытый ответ, ошибка загрузки. Старые эталоны удаляются, новые снимаются `screenshotUpdate` **только после того, как пользователь просмотрит новые скриншоты** и подтвердит их.

## Risks / Trade-offs

- [Скриншотные тесты и хук `ui-check.sh` падают, пока не сняты новые эталоны] → при правках `static/` до согласования эталонов падения скриншотов ожидаемы и не исправляются откатом; e2e при этом обязаны проходить. Эталоны снимаются одной задачей в конце вёрстки после подтверждения пользователя.
- [Закладки на `/` с формой ломаются] → навигация на каждой странице; формат данных и API не меняются.
- [Дублирование навигации в трёх HTML] → три небольших файла; тест навигации ловит расхождения.
- [Случайность в e2e недетерминирована] → e2e проверяют свойства (размер, отсутствие повторов, принадлежность к базе), а не конкретный порядок; конкретные наборы — только в скриншотах с подменённым API и в JUnit с фиксированным зерном.
- [Пользовательский `data/cards.csv` меняет формат при первой записи после обновления] → чтение старого формата покрыто тестами; перезапись атомарная; откат описан в решении 1 и README.
- [Запрос отметки замедляет переход к следующему вопросу] → локальный сервер отвечает за миллисекунды; кнопки блокируются на время запроса, чтобы не было двойных нажатий.
- [Длинный текст не помещается в квадрат] → прокрутка внутри карточки; проверяется скриншотом с длинным вопросом.
