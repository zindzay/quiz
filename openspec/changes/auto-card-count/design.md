# Design

## Context

Скилы `/quiz-from-web-page` и `/quiz-from-pdf` генерируют карточки по общим правилам `tools/quiz-import/card-rules.md` и отправляют их через `post_cards.py`. После `complete-web-page-import` веб-скил получает полный текст страницы, разбитый на разделы и части (`fetch_page.py`, `meta.json`, `chunk-XX.md`). PDF-скил (`import-quiz-from-pdf`) режет выбранный диапазон скриптом `tools/quiz-import/split_pdf.swift` на части `part-XX.pdf` по 10 страниц (Read без параметра `pages` читает не больше 10 страниц, а `pages` требует poppler) и берёт квоты частей из его `meta.json`. Количество по умолчанию сейчас — 10 в обоих скилах. Требования — delta-спецификации этого изменения.

## Goals / Non-Goals

**Goals:**
- Без явного количества набор карточек покрывает **все** ключевые положения источника, а число карточек определяется содержанием.
- Полнота проверяема: явный список положений и детерминированная сверка «положение → карточка».
- Одна и та же логика для веб-страниц и PDF.

**Non-Goals:**
- Ранжирование положений по важности и отбор «главного»: автоматический режим означает полный охват, а не выборку.
- Изменения API и формата CSV: связь положений с карточками живёт только во время импорта.

## Decisions

### 1. Автоматический режим — два прохода по каждой части
Для каждой части источника (веб — `chunk-XX.md`, PDF — `part-XX.pdf` по 10 страниц из `split_pdf.swift`):
1. **Выделить ключевые положения** — атомарные утверждения, которые стоит проверить: определение, факт, число или дата, причина и следствие, шаг процесса, сравнение, ограничение или исключение. Каждое положение — одна строка текстом источника, с указанием раздела.
2. **Сделать по карточке на каждое положение** по правилам `card-rules.md`.

Положения, повторяющиеся в разных частях (например, во введении и в разделе), объединяются: на одно положение — одна карточка.
- *Альтернатива — число карточек по объёму текста (одна на N символов).* Это просто, но не гарантирует охвата: плотный раздел недопокрыт, «водянистый» — перепокрыт.
- *Альтернатива — один проход «сгенерируй сколько нужно».* Тогда нечего сверять, и полноту не проверить.

### 2. Файл покрытия и скрипт `tools/quiz-import/coverage.py`
Скил ведёт рядом с файлом карточек файл покрытия `coverage.json`:
```json
{"sections": [{"id": "s3", "title": "Коды состояния", "points": [{"id": "s3-p1", "text": "...", "card": 7}]}]}
```
Здесь `card` — индекс карточки в JSON-массиве карточек или `null`. Сам файл карточек не меняется: в нём по-прежнему только `question` и `answer`, как требует `card-rules.md`.

Для веб-страницы раздел в `coverage.json` — раздел из `meta.json` `fetch_page.py` (`id` вида `s3`). Для PDF раздел — часть документа из `meta.json` `split_pdf.swift`: `id` вида `p1`, `title` — диапазон страниц («стр. 1–10»). Поэтому разбивка отчёта по разделам для PDF и есть разбивка по диапазонам страниц, которую требует спецификация.

Команды скрипта:
- `coverage.py check COVERAGE CARDS` — проверяет, что у каждого положения есть существующая карточка, а каждая карточка привязана хотя бы к одному положению. Также проверяет, что у каждого раздела с положениями есть хотя бы одна карточка. Код 0 — всё покрыто, код 3 — есть непокрытые положения (их список печатается в stdout в JSON), код 1 — ошибка формата.
- `coverage.py report COVERAGE CARDS` — печатает строку «ключевых положений: X, покрыто: Y» и таблицу «раздел → положений → карточек».

Сверку выполняет скрипт, а не модель «на глаз». Требование «Проверка полноты покрытия» становится воспроизводимым и покрывается юнит-тестами.

### 3. Цикл досоздания
Скил выполняет `coverage.py check`. При коде 3 он создаёт карточки для перечисленных положений, обновляет оба файла и проверяет снова — не больше 3 итераций. Если после трёх итераций остались непокрытые положения, скил не скрывает это: список попадает в отчёт.

### 4. Порог 150 карточек
Когда сверка прошла и карточек больше 150, скил печатает `coverage.py report` и спрашивает пользователя:
- отправить все;
- отменить;
- указать количество явно — тогда скил запускается заново в обычном режиме с этим числом.

Ответ ожидается от пользователя, а не выбирается скилом. Порог защищает от случайного импорта сотен карточек из огромного документа, но не ограничивает полноту, если пользователь её подтвердил.

### 5. Явное количество
Поведение не меняется: 1–50, квоты по разделам (веб — `fetch_page.py --count N`) или по частям (PDF — `split_pdf.swift --count N`). Число 50 остаётся верхней границей только для явного режима.

### 6. Изменения в инструментах
- `fetch_page.py --count auto`: квоты не считаются (`quota: null`), а разделы, части и `skipped_reason` записываются как обычно. Справочные разделы в автоматическом режиме тоже пропускаются.
- `split_pdf.swift --count auto`: квоты не считаются (`quota: null`); проверка PDF и пароля, лимит 100 страниц без диапазона и нарезка по 10 страниц — как обычно. Сейчас `--count` принимает только 1–50, поэтому без этого режима PDF-скил не может нарезать документ в автоматическом режиме.
- `card-rules.md`, новый раздел «Полный охват (автоматический режим)»: определение ключевого положения с примерами, правило «одно положение — одна карточка», объединение повторов, формат `coverage.json`.
- В обоих `SKILL.md`: если количество не указано — автоматический режим, шаги «положения → карточки → `coverage.py check` → досоздание → порог 150 → `post_cards.py post` → отчёт с `coverage.py report`». В `allowed-tools` добавляется `Bash(python3 tools/quiz-import/coverage.py:*)`.

### 7. Тестирование
- `test_coverage.py` (`unittest`) проверяет:
  - полное покрытие → код 0;
  - непокрытое положение → код 3 и его `id` в выводе;
  - карточка без положения → код 3;
  - раздел без карточек → код 3;
  - индекс карточки вне массива → код 1;
  - `report` выдаёт правильные числа и разбивку.
- Тест `fetch_page.py --count auto`: `quota` у всех разделов равна `null`, справочные разделы помечены.
- Тест `split_pdf.swift --count auto` в `test_split_pdf.py`: `quota` у всех частей равна `null`, а сами части те же, что при `--count 10`.
- Ручной прогон сценариев спецификаций на отдельном экземпляре приложения с временным файлом данных:
  - веб: короткая страница (несколько фактов → столько же карточек), длинная статья (больше 10 карточек, все разделы), отчёт покрытия, искусственно пропущенное положение досоздаётся;
  - PDF: короткий документ, лекция `sections.pdf`, отчёт по диапазонам страниц;
  - порог: страница или документ, дающие больше 150 карточек (например, длинная статья Википедии) → вопрос пользователю без отправки.

## Risks / Trade-offs

- [Модель выделит не все ключевые положения — сверка проверяет только те, что попали в список] → чёткое определение и примеры в `card-rules.md`, выделение по небольшим частям (до ~12 000 символов или 10 страниц), правило «каждый раздел даёт хотя бы одну карточку» проверяет скрипт. Полную гарантию от пропуска на этапе выделения дать нельзя, и это отмечено в отчёте как «покрытие выделенных положений».
- [Импорт без количества заметно дороже по токенам: два прохода и сверка] → осознанная цена полноты. Явное количество остаётся быстрым путём.
- [Слишком мелкое дробление — карточки на тривиальные детали] → в `card-rules.md` закреплено, что ключевое положение — то, что стоит проверить; служебные детали (даты правок, имена авторов страницы) не считаются.
- [Порог 150 прерывает работу вопросом] → срабатывает только на очень больших источниках. Ответ «отправить все» сохраняет полноту.

## Migration Plan

Вызовы с явным количеством работают как раньше. Вызовы без количества меняют поведение: вместо 10 карточек — полный охват. Откат — вернуть прежние `SKILL.md`; `coverage.py` ни на что больше не влияет.
