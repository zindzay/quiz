# Design

## Context

Сейчас `/quiz-from-web-page` получает страницу через WebFetch. Этот инструмент передаёт HTML вспомогательной модели вместе с запросом и возвращает её ответ. На длинных страницах ответ — пересказ, к тому же модель видит не больше 100 000 символов за вызов. Проверка на ru.wikipedia.org/wiki/HTTP (около 133 000 символов) дала текст примерно на 2 000 символов. Отправку, дубликаты и правила генерации уже обеспечивают `tools/quiz-import/post_cards.py` и `card-rules.md`, их это изменение не трогает. Требования — delta-спецификация `quiz-from-web-page` в этом изменении.

## Goals / Non-Goals

**Goals:**
- Полный основной текст страницы без участия вспомогательной модели.
- Детерминированные и тестируемые: извлечение текста, деление на части, распределение квот карточек.
- Отчёт, из которого видно, какая часть страницы покрыта.

**Non-Goals:**
- Выполнение JavaScript. Для таких страниц остаётся запасной путь через WebFetch с предупреждением.
- Сторонние Python-пакеты (readability, BeautifulSoup) — только стандартная библиотека, как у `post_cards.py`.
- Изменение `card-rules.md` и `post_cards.py`.

## Decisions

### 1. Скрипт `tools/quiz-import/fetch_page.py`
```
fetch_page.py URL --count N --out DIR
```
Скрипт загружает страницу через `urllib` с понятным `User-Agent` (`quiz-import/1.0`): Википедия и часть сайтов отклоняют запросы без него. Кодировка берётся из `Content-Type` или `<meta charset>`, по умолчанию UTF-8 с заменой ошибочных байтов. Результат записывается в `DIR`:
- `chunk-01.md`, `chunk-02.md`, … — текст частей в Markdown (заголовки, абзацы, списки, таблицы строками через ` | `, блоки кода);
- `meta.json` — `url`, `title`, `total_chars`, `processed_chars`, `truncated`, список разделов (`title`, `chars`, `chunk`, `quota`, `skipped_reason`) и список частей.

Коды выхода:
- `0` — готово;
- `1` — неверные аргументы;
- `3` — основного текста меньше 500 символов, нужен запасной путь;
- `4` — HTTP-ошибка или недоступный хост, сообщение в stderr.

- *Альтернатива — WebFetch с параметром `offset` по частям.* Пересказ и сокращение остаются, потому что каждую часть всё равно обрабатывает вспомогательная модель.
- *Альтернатива — `curl` плюс разбор HTML моделью.* Разметка HTML в несколько раз больше текста, это дорого по токенам и не воспроизводимо.

### 2. Выделение основного текста (`html.parser`)
1. Корень: `<main>`, иначе самый объёмный по тексту `<article>`, иначе `<body>`.
2. Выбрасываются: `script`, `style`, `noscript`, `template`, `svg`, `iframe`, `form`, `button`, `nav`, `header`, `footer`, `aside`, элементы с `role` = `navigation` / `banner` / `contentinfo` / `search`, `hidden`, `aria-hidden="true"`.
3. Выбрасываются элементы, у которых в `class` или `id` есть слово из списка `nav`, `menu`, `footer`, `sidebar`, `cookie`, `comments`, `breadcrumb`, `toc`, `mw-editsection`, `reference` (сравнение по словам, а не подстрокам).
4. Пробелы схлопываются, пустые абзацы удаляются.

Эвристики в шагах 2 и 3 покрываются тестами на фикстурах. Ошибиться в сторону «оставить лишнее» безопаснее, чем потерять содержимое: служебный текст потом отфильтруют правила генерации.

### 3. Разделы, части и лимит
- **Крупный раздел** — фрагмент от `<h2>` до следующего `<h2>`. Если `<h2>` на странице нет — от `<h1>`. Вводный текст до первого заголовка — раздел «Введение».
- Разделы без осмысленного содержания получают `quota = 0` и `skipped_reason`:
  - справочные по заголовку: «Примечания», «Литература», «Ссылки», «См. также», «References», «See also», «External links», «Notes», «Further reading»;
  - короче 300 символов.
- **Части** — разделы, последовательно упакованные до ~12 000 символов. Раздел длиннее 12 000 символов делится по абзацам. Абзац и блок кода не разрываются. Склейка всех частей должна давать весь извлечённый текст (проверяется тестом).
- **Лимит** — 500 000 символов основного текста. Сверх него разделы отбрасываются целиком с конца. `truncated = true`, `processed_chars < total_chars`.

### 4. Квоты карточек считает скрипт
Пусть `S` — разделы с осмысленным содержанием, а `N` — запрошенное количество карточек.
- `N ≥ |S|`: каждый раздел из `S` получает 1, а остаток `N − |S|` распределяется пропорционально объёму методом наибольших остатков.
- `N < |S|`: выбираются `N` разделов, равномерно разнесённых по странице (индексы `round(i · |S| / N)`), по 1 карточке.

Сумма квот всегда равна `N`. Расчёт в скрипте, а не в промпте, делает распределение воспроизводимым и тестируемым. Требование «Распределение карточек по разделам» проверяется юнит-тестами.

### 5. Новый порядок работы скила
1. Аргументы и `post_cards.py check` — без изменений.
2. `fetch_page.py URL --count N --out <scratchpad>/page-<время>`.
   - Код `4` — остановка, как сейчас при ошибке загрузки.
   - Код `3` — запасной путь (решение 6).
3. Прочитать `meta.json`, затем по очереди каждый `chunk-XX.md` через Read и сгенерировать для разделов этой части ровно их квоту по `card-rules.md`. Если в разделе материала меньше квоты — меньше. Карточки накапливаются в одном JSON.
4. `post_cards.py post`, затем отчёт: прежние пункты, строка покрытия `обработано X из Y символов (P %)`, разделы с числом карточек, пропущенные справочные разделы, предупреждение при `truncated`.

Части читаются по одной: в контексте одновременно находится не больше ~12 000 символов страницы.

### 6. Запасной путь
При коде `3` скил использует WebFetch с прежним запросом. Если ответ сообщает о сокращении, скил повторяет запрос с `offset`, пока страница не закончится. Генерация идёт по прежней схеме, а в отчёте пишется: «текст получен через WebFetch в обработанном виде — полнота не гарантируется».

### 7. Тестирование
- `test_fetch_page.py` (`unittest`, локальный `http.server` с HTML-фикстурами в `tools/quiz-import/fixtures/`). Проверяются:
  - выбор `<main>` и удаление навигации, футера и `aside`;
  - удаление элементов по `class` и `role`;
  - заголовки, списки, таблицы и код в Markdown;
  - кодировка `windows-1251`;
  - код 4 при ответе 404 и код 3 для страницы, собранной JavaScript;
  - статья на 130 000 символов: все части не больше 12 000, склейка равна извлечённому тексту;
  - страница на 600 000 символов: `truncated`, обработано не больше 500 000;
  - квоты: 10 карточек на 5 разделов — у каждого раздела хотя бы 1, сумма 10; 3 карточки на 8 разделов — 3 разных раздела, включая раздел из второй половины;
  - справочные разделы получают квоту 0.
- Ручной прогон скила: статья Википедии «HTTP», 10 карточек — есть карточки из второй половины статьи, покрытие 100 %; страница, собранная JavaScript, — запасной путь с предупреждением; повторный прогон прежних сценариев `quiz-from-web-page` (404, короткая страница, дубликаты).

## Risks / Trade-offs

- [Эвристики извлечения ошибаются на необычной вёрстке: теряют содержимое или оставляют мусор] → приоритет `<main>`/`<article>`, удаление по словам, а не подстрокам, фикстуры в тестах. Отчёт о покрытии покажет аномально малый объём. Запасной путь срабатывает при тексте меньше 500 символов.
- [Импорт длинных страниц дороже по токенам: 130 000 символов — это около 11 частей] → это осознанная цена полноты. Лимит 500 000 символов ограничивает худший случай.
- [Сайт отклоняет запросы скрипта (403, защита от ботов)] → код 4 с текстом ответа. Пользователь может повторить позже. Запасной путь через WebFetch при 403 не используется, потому что сайт явно отказал.
- [`User-Agent` скрипта отличается от браузерного, и сайт отдаёт другую вёрстку] → `<main>`/`<article>` есть почти во всех вариантах вёрстки. Иначе — отчёт о покрытии и запасной путь.

## Migration Plan

Скил и скрипт обновляются вместе. Откат — вернуть прежний `SKILL.md`: `fetch_page.py` ни на что больше не влияет. Основная спецификация `quiz-from-web-page` должна существовать до архивации, поэтому сначала архивируется `import-quiz-from-web-page`.
