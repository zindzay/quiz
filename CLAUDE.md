# CLAUDE.md

Этот файл задаёт контекст для Claude Code при работе с репозиторием.

## О проекте

**quiz** — веб-приложение с карточками «вопрос — ответ» (flashcards).

- **Бэкенд:** Java 27, Spring Boot 4 (Spring MVC), сборка Gradle (Kotlin DSL), пакет `org.valgor.quiz`.
- **Хранилище:** локальный CSV-файл вместо СУБД (Apache Commons CSV).
- **Фронтенд:** статичные HTML + vanilla JS в `src/main/resources/static/`, их раздаёт Spring Boot.
- **Процесс разработки:** spec-driven через [OpenSpec](https://github.com/Fission-AI/OpenSpec).

Обоснование стека — в `design.md` изменения `add-card-view-and-create`.

## Команды

```bash
./gradlew bootRun        # запуск на http://localhost:8080
./gradlew build          # компиляция + тесты
./gradlew test           # только тесты (JUnit 5 / Jupiter)
./gradlew test --tests "org.valgor.quiz.web.CardApiTest"   # один тестовый класс
./gradlew clean
```

Настройки (`src/main/resources/application.properties`) переопределяются переменными окружения:

| Свойство          | Переменная       | По умолчанию     |
|-------------------|------------------|------------------|
| `quiz.data-file`  | `QUIZ_DATA_FILE` | `data/cards.csv` |
| `server.port`     | `SERVER_PORT`    | `8080`           |

Пример: `QUIZ_DATA_FILE=/tmp/cards.csv SERVER_PORT=9090 ./gradlew bootRun`.

API: `GET /api/cards`, `GET /api/cards/{id}`, `POST /api/cards` (`{"question", "answer"}`); ошибки — `{"error": "..."}`.

## Рабочий процесс OpenSpec

Любая функциональность появляется только через изменение (change) OpenSpec. Код без согласованной спецификации не пишется.

```
openspec/
├── config.yaml          # schema: spec-driven + контекст проекта
├── specs/               # актуальные спецификации (источник истины о поведении)
└── changes/             # активные изменения
    └── archive/         # завершённые изменения
```

Цикл работы:

1. **Исследование** (по желанию) — `/opsx:explore`: обсудить идею, ничего не меняя в коде.
2. **Предложение** — `/opsx:propose <описание>`: создаёт `changes/<id>/` с `proposal.md`, `design.md`, `tasks.md` и delta-спеками в `specs/`.
3. **Ревью** — пользователь читает и утверждает артефакты. Правки плана — `/opsx:update`.
4. **Реализация** — `/opsx:apply <id>`: выполнять задачи из `tasks.md` по порядку, отмечая `- [x]` после каждой.
5. **Архив** — `/opsx:archive <id>`: delta-спеки сливаются в `openspec/specs/`, изменение уходит в `archive/`.

Правила:

- Не начинать реализацию, пока пользователь не утвердил proposal.
- Если в ходе реализации выясняется, что спецификация неверна или неполна, — остановиться и обновить артефакты изменения (`/opsx:update`), а не молча отступать от них.
- Требования в спеках формулируются через `SHALL`/`MUST` и сценарии `WHEN … THEN …`; каждый сценарий должен быть покрыт тестом.
- Одно изменение — одна связная возможность (например, «просмотр карточек», «добавление карточки», «режим тренировки»), а не всё приложение сразу.
- Артефакты OpenSpec пишутся на русском языке; идентификаторы изменений — kebab-case на английском (`add-card-crud`).

## Предметная область

**Карточка (Card)** — минимальная модель:

| Поле       | Тип    | Описание                          |
|------------|--------|-----------------------------------|
| `id`       | string | Уникальный идентификатор (UUID)   |
| `question` | string | Текст вопроса, не пустой          |
| `answer`   | string | Текст ответа, не пустой           |

Дополнительные поля (тема/колода, статистика ответов, даты) добавляются только через OpenSpec-изменение с обновлением формата CSV.

## Хранение в CSV

- Путь к файлу задаётся конфигурацией (по умолчанию `data/cards.csv`); при отсутствии файл создаётся с заголовком.
- Формат: UTF-8 без BOM, разделитель `,`, первая строка — заголовок (`id,question,answer`), экранирование по RFC 4180 (кавычки, запятые и переводы строк внутри значений).
- Не парсить CSV через `split(",")` — использовать библиотеку (например, Apache Commons CSV или OpenCSV) либо корректный парсер с тестами на экранирование.
- Доступ к файлу инкапсулирован за интерфейсом репозитория (`CardRepository`); остальной код не знает, что хранилище — CSV. Это позволит заменить хранилище без изменения бизнес-логики.
- Запись атомарная: писать во временный файл в той же директории и заменять через `Files.move(..., ATOMIC_MOVE)`, чтобы сбой не повредил данные.
- Конкурентный доступ внутри процесса синхронизировать (например, `ReadWriteLock`); предполагается один экземпляр приложения на файл.
- Файлы данных (`data/`) не коммитятся; в репозитории может лежать только пример `data/cards.example.csv`.
- Приложение держит карточки в памяти и перезаписывает файл целиком: **редактировать CSV вручную только при остановленном приложении**, иначе правки будут потеряны. Повреждённый файл (неверный заголовок, сломанные кавычки) не даёт приложению стартовать и не перезаписывается.

## Архитектура и код

- Слои: `web` (контроллеры/обработчики HTTP) → `service` (бизнес-логика, валидация) → `repository` (CSV). Зависимости направлены только внутрь.
- Модель — неизменяемые `record`.
- API — REST + JSON; ошибки валидации возвращаются с кодом 400 и понятным сообщением, отсутствующая карточка — 404.
- Новые зависимости добавлять в `build.gradle.kts` с явным обоснованием в `design.md` соответствующего изменения.

## Тестирование

- JUnit 5. Тесты лежат в `src/test/java` в том же пакете, что и тестируемый код.
- Репозиторий CSV тестируется на реальных файлах во временной директории (`@TempDir`), включая значения с запятыми, кавычками и переносами строк.
- Сервисный слой тестируется изолированно от файловой системы.
- HTTP API — `@SpringBootTest` + `MockMvcTester`; путь к данным задавать через `@DynamicPropertySource` на `@TempDir`. В тестах с `SpringApplicationBuilder` передавать настройки аргументами `run("--quiz.data-file=...")`: `properties(...)` перекрывается `application.properties`, и тест запишет в настоящий `data/cards.csv`.
- Отдачу статики (`/` → `index.html`) проверять на реальном сервере (`RANDOM_PORT`): MockMvc не выполняет forward.
- Перед тем как отметить задачу в `tasks.md` выполненной, `./gradlew build` должен проходить.

## E2E-тесты интерфейса

Поведение сценариев `openspec/specs/cards-web-ui/spec.md` проверяется автотестами в браузере (Playwright, Chromium) на настоящем приложении — ручная проверка в браузере не нужна.

```bash
./gradlew e2eTest     # входит в ./gradlew check и build
cd ui-tests && npx playwright show-report playwright-report-e2e   # отчёт последнего прогона
```

- Тесты: `ui-tests/e2e/cards-page.spec.ts`, конфиг `ui-tests/playwright.e2e.config.ts`; результаты и трейсы падений — `ui-tests/test-results-e2e/`.
- Фикстура `app` (`ui-tests/e2e/app-fixture.ts`) поднимает отдельный экземпляр jar на свободном порту с пустым временным файлом данных на каждый тест: `app.createCard()` — подготовка данных через API, `app.listCards()` — проверка хранилища, `app.stop()` — остановка сервера.
- Элементы искать по ролям, подписям и текстам (`getByRole`, `getByLabel`, `getByText`), не по CSS-классам. Карточки списка имеют роль `button`, поэтому ищутся как `getByRole('list').getByRole('button')`.
- Каждый новый сценарий UI в спецификации сопровождается e2e-тестом в том же изменении. Шаги «проверить вручную в браузере» в `tasks.md` не используются, если сценарий можно автоматизировать.
- Новый тест проверять «мутацией»: временно сломать соответствующий код и убедиться, что тест падает.

## Скриншотные тесты

Внешний вид веб-интерфейса зафиксирован эталонными скриншотами (Playwright Test, Chromium) в `ui-tests/`.

```bash
./gradlew screenshotTest     # сравнить с эталонами; входит в ./gradlew check и build
./gradlew screenshotUpdate   # перезаписать эталоны — только при намеренном изменении вида
cd ui-tests && npx playwright show-report   # HTML-отчёт последнего прогона
```

- Тесты: `ui-tests/tests/cards-page.spec.ts`; эталоны: `ui-tests/tests/__screenshots__/` (коммитятся).
- Ответы `/api/cards` подменяются в каждом тесте (`ui-tests/tests/fixtures.ts`); статику отдаёт собранный jar на порту 18080 (`QUIZ_UI_TEST_PORT`) с временным файлом данных — `data/` не затрагивается.
- Вариант темы/вьюпорта выбирается тегом в названии теста: без тега — светлая тема 1280×800, `@dark` — тёмная, `@mobile` — 390×844.
- При расхождении: `ui-tests/test-results/<тест>/` содержит `*-expected.png`, `*-actual.png`, `*-diff.png`.
- Эталоны снимаются на macOS (суффикс `-darwin`); на Linux/CI нужны свои эталоны — пока не настроено.
- Первый запуск скачивает Node 24 (в `.gradle/nodejs`) и Chromium (в `~/Library/Caches/ms-playwright`).
- Новое состояние интерфейса (новый экран, элемент, ошибка) — добавить скриншотный тест в том же изменении.

**Правило обновления эталонов.** Расхождение скриншотов по умолчанию считается регрессией: исправлять код, а не эталоны. `screenshotUpdate` запускается только если изменение внешнего вида — цель задачи, и только после того, как пользователь посмотрел список изменившихся скриншотов с путями к `*-diff.png` и подтвердил.

**Хук Claude Code.** `.claude/settings.json` запускает `.claude/hooks/ui-check.sh` после каждого `Edit`/`Write` в `src/main/resources/static/`: он прогоняет `screenshotTest` и `e2eTest`. При падении хук возвращает список упавших тестов (код 2): скриншоты — по правилу выше, e2e — исправлять код. Правки вне `static/` хук пропускает сразу; правки Java-кода проверяет `./gradlew build`.
